Building microservices with a Clean Architecture design

May 8, 2020 Mahmoud Sharqawi

Building microservices with a Clean Architecture design involves using the principles of Clean Architecture within each individual microservice to ensure the core business logic is independent of external concerns like databases, frameworks, or UI. This combination enhances modularity, testability, and scalability.

Core Principles

  • Separation of Concerns:The architecture divides the system into distinct layers, each with a specific responsibility.
  • Dependency Inversion (The Dependency Rule):High-level business logic should not depend on low-level implementation details. Both should depend on abstractions (interfaces). Dependencies flow inward towards the core domain.
  • Domain-Centric: Each microservice should encapsulate a specific business capability or "Bounded Context," managing its own data and logic, as defined by Domain-Driven Design (DDD) principles.
  • Independent Deployability & Testability: The clear boundaries ensure that components can be developed, tested, and deployed in isolation.

Internal Structure of a Clean Microservice

Each microservice typically follows the layered structure below:

Domain Layer (Core):

The innermost layer contains the essential business rules, entities, and value objects. This is the most stable part and has no dependencies on outside layers. It encapsulates the core business logic and is independent of external concerns like databases, frameworks, or UI.

Application Layer:

This layer contains application-specific business rules and use cases (e.g., commands and queries using the CQRS pattern). It orchestrates domain entities to perform tasks and defines interfaces (ports) that external layers must implement.

Infrastructure Layer:

This outermost layer handles all external concerns, such as database interactions (e.g., Entity Framework Core implementations), external APIs, messaging with brokers (like RabbitMQ), and caching. It implements the interfaces defined in the Application Layer.

Presentation Layer (API):

For services that expose an HTTP API, this layer (e.g., controllers) handles HTTP requests, maps them to commands/queries, and returns responses.
